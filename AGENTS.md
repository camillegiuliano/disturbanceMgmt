# disturbanceMgmt — agent guide

Adapted from the `PredictiveEcology/AI` template (https://github.com/PredictiveEcology/AI;
cloned locally at `~/GitHub/AI`). Scope: this one R package folder. Sibling repos under
`~/GitHub` (e.g. `Biomass_genericDisturbance`, `LandRCBM`, `spadesCBM`) are **outside this
folder and read-only** unless the user grants write access for a specific path — re-ask
each time.

## What this package is

An accessory **R package** (not a SpaDES module) in the PredictiveEcology ecosystem,
intended to support disturbance and management work in `SpaDES` modules. It is currently a
**bare scaffold**: no functions have been written and the package's scope has not been
settled. `Title`, `Description`, and `Authors@R` in `DESCRIPTION` are placeholders marked
`TODO`. See "Open decisions" below — do not fill these in by guessing.

Scaffold contents: `DESCRIPTION`, `R/disturbanceMgmt-package.R`, `tests/testthat.R` +
`tests/testthat/`, `man/`, `NEWS.md`, `README.md`, `LICENSE.md` (GPL-3), `.Rbuildignore`,
`.gitignore`, `disturbanceMgmt.Rproj`, and `.github/workflows/` thin callers to
`PredictiveEcology/actions@main`.

## Where the knowledge lives

- **SpaDES toolkit** (the framework this ecosystem builds on):
  https://spades.predictiveecology.org/. A simulation is a `simList`; `simInit()` builds
  it, `spades()` runs it. Modules communicate **only** through named `simList` objects —
  one module's `createsOutput` is another's `expectsInput`. That name is a contract.
  A package like this one sits *below* the modules: it holds reusable logic that more than
  one module (or a module and an analysis script) calls.
- **LandR** is the forest-landscape model system built on that toolkit; if this package
  ends up touching cohort data, pixel groups, or species/ecoregion tables, LandR
  conventions apply and LandR-specific skills win over the general SpaDES ones.
- **Skills** (install via `/plugin`, marketplace `PredictiveEcology/AI`):
  `spades-package-development` (stub), `spades-module-development`,
  `landr-package-maintenance`, `testing`, `code-documentation`. Get these before writing
  new ones.

## Working rules

### The user owns the science

The user is the authority on the ecological process being modelled; the assistant
contributes programming knowledge. If a request is vague about the phenomenon ("add the
harvest function"), **ask what process, at what spatial and temporal scale, with what
inputs and outputs** before writing code. Do not invent ecological behaviour.

Flag — do not silently implement — anything that contradicts process logic:
timestep/rate mismatches, unit or per-pixel/per-hectare confusion, impossible states
(negative biomass or age), or biomass/carbon created or destroyed without a corresponding
flux.

### Changes to existing code need approval

Explain what will change, why, and the downstream effects (including on modules that call
this package), then wait. Prefer the smallest change that does the job; do not refactor
opportunistically. Fix defects where they live, naming the root cause with `file:line` — a
workaround at the call site is not a fix, and never stack a patch on a patch.

### Editing files

- **Edit `.R` files with `bash` (heredoc) or an in-place `python3` script — never the
  `edit`/`write` editor tools.** Format-on-save can reformat the whole file and produce
  large unwanted diffs. Markdown, YAML, `DESCRIPTION`, and `.Rmd` are fine through the
  editor tools.
- **After any change, verify the diff**: `git diff <file>` and `git diff --stat`, and
  confirm only what was asked changed. For documentation-only R edits,
  `git diff <file> | grep '^[+-]' | grep -v '^[+-]#'` should return nothing.
- Do not reformat or restyle unasked. Match the file's existing brace style, operator
  spacing, and blank-line layout.
- Never `git commit` unless explicitly told to. Stage specific paths; never `git add -A`
  or `git add .`. Dry-run destructive commands first.

### Package anatomy and workflow

- Standard R package layout: `DESCRIPTION`, `NAMESPACE`, `R/`, `man/`, `tests/testthat/`,
  `NEWS.md`. The devtools loop is `document()`, `load_all()`, `test()`, `check()`.
- **`NAMESPACE` and `man/*.Rd` are generated by roxygen2 — never hand-edit them.**
- Hard dependencies go under `Imports:`, test- and vignette-only ones under `Suggests:`;
  GitHub dependencies are pinned in `Remotes:`. Keep `Language: en-CA`.
- Versions are four-part development versions (e.g. `0.0.1.9000`); increment the fourth
  component for development changes, and **every bump needs a matching `NEWS.md` entry**.
- Raising this package's minimum version of a dependency may require updating `reqdPkgs`
  pins in modules that use it — check before assuming it is self-contained.
- Use `@importFrom` rather than `library()`; declare non-standard-evaluation symbols
  (e.g. `data.table` column names) with `utils::globalVariables()`.

### Coding conventions

- `data.table` and the base pipe `|>` (not `%>%`), for performance and memory at landscape
  scale. `copy()` a `data.table` before modifying it; `setkey()` before joins, with
  `nomatch = 0`; use `.SD`, `by=`, and `..cols` for group-wise work.
- camelCase for column names and helper functions; PascalCase is reserved for major event
  functions in modules.
- Store age, biomass, and ANPP as integers, using `asInteger()` (rounds) rather than
  `as.integer()` (truncates). Compare floating-point values with `fpCompare` operators.
- `reproducible::Cache()` and `prepInputs()` for expensive or downloaded steps.
  `prepInputs()` does not cache on its own — wrap it in `Cache()`. Generally **do not
  cache stochastic computations**.
- **Memory-efficient R:** avoid `Map()`, `do.call()`, and the `apply` family — use `purrr`
  (`map()`, `map2()`, `pmap()`, `walk()`). Avoid `as.formula()` (it captures its
  environment); build a `call()` or `bquote()` instead. Do not define closures inside large
  environments. Do not add `compiler::cmpfun()` reflexively.
- `message()` for progress, `warning()` for a relaxed assumption or fallback, `stop()` for
  conditions that make continuing unsafe. **State which was chosen and why**, and flag the
  tradeoff — a `warning()` is easy to miss in a long batch or HPC run.
- Check for an existing function before writing a new one: this package, the project's
  other packages, then CRAN. **Flag any new dependency before adding it**, with the reason
  and whether an existing dependency could serve.
- Ask whether logic belongs **here** (used in more than one place, so there is a single
  source of truth) or in a **module** (specific to that module's behaviour).

### Documentation

Document every function with a `#'` roxygen block. Exported functions need a title, a
description, every `@param`, a `@return`, and `@export`; document the columns or structure
of rich `data.table` arguments and return values. Internal helpers get `@keywords
internal`, plus `@noRd` when no help page is wanted — but ask the user first before adding
`@keywords internal` to an **exported** function. Use `@inheritParams` to avoid duplicating
parameter docs, after confirming the inherited parameter genuinely matches. Preserve
`@author`. **Never reorder a function's arguments** as part of a documentation change.

### Testing

Do not create tests unless asked. When asked, use `testthat` under `tests/testthat/`, with
small fixed in-memory `data.table`s and tiny rasters with known expected values rather than
random data; if randomness is unavoidable, set a seed (a random integer, not 42). Use
`tempdir()` for caches and stub downloads. Run with `devtools::test()`. Prompt the user to
run module integration tests after any change that crosses a package/module boundary.

### CI

Use the shared reusable workflows at the shared ref, `PredictiveEcology/actions@main`; the
files in `.github/workflows/` are thin callers. Never hand-roll or hand-patch a per-repo
copy of setup the shared workflow already does. When one fails, check the pin before
blaming the action.

### Writing for people

Documentation targets **ecologists and other scientists, not software engineers**:
minimize jargon, define any technical term you must use, and match the existing file's tone
and markup rather than restyling it. PRs, issues, and comments lead with the outcome and
are usually three to six sentences — plain English, no "comprehensive", "robust", or
"leverage", no headers or bullets in a short comment, and never close by calling the work
"ready". Comment the *why*, not the *what*; in a pipeline, put the comment on the line
before the step. Keep punctuation **outside** formatting unless it is part of a name.

### Session hygiene

Keep a durable session log from the point real work starts, updated at milestones — a
decision, a settled question, an abandoned direction — with **what was ruled out** and
**the exact next step**. Verify claims rather than inferring them: "probably flaky" is a
hypothesis, not a finding. When the session grows long, suggest `/compact` and
`/savememory`.

## Open decisions (ask, do not assume)

1. What the package is for — its `Title` and `Description`, and the boundary between what
   lives here and what stays in a module such as `Biomass_genericDisturbance`.
2. `Authors@R`: the user's name, email, and optional ORCID. The crown copyright holder
   (`His Majesty the King in Right of Canada…`) is already in place, per the user's choice.
3. Whether this is a PredictiveEcology-org repo or a personal one — the URLs in
   `DESCRIPTION` and `README.md` currently assume `PredictiveEcology/disturbanceMgmt`.
4. The default branch and fork/upstream arrangement once the GitHub repo exists. New
   repositories should use `main`. `gh` is not authenticated on this machine, so the user
   must create the remote.
5. Which modules and chains will depend on this package, so function and argument names
   follow their patterns.
